## 1. CONFIRMED LANDMINES (ranked by blast radius)

### 1. Job-work orders track their life in two status fields that no longer agree
Every job sent to a dyer or printer has an old status field and a new one, and different screens update different ones — cancelling a job updates only the new field, so the old one still says "at mill." The bite: you issue 500m greige to a dyer, the dyer declines, office cancels the job and the 500m is credited back to stock — days later the physical rolls arrive and the warehouse, still seeing the job on the "at processor" list with a Receive button, receives it through GRN, so the same 500m now exists twice and MRP trusts inventory you don't have. This touches the daily job-work issue/receive flow, and the live database already holds one diverged row (jwoStatus CANCELLED, old status READY_TO_SEND); the Section-143 dashboard also counts cancelled jobs forever while the statutory report correctly excludes them, so the two reports disagree today.
**Technical:** `job_work_orders.status` (legacy) vs `jwoStatus`. Writers: both-columns `job-work-issuance.service.ts:562-566`, `external-process.service.ts:338/523-531`; legacy-only `grn.service.ts:343-362, 673-686`, `dyeing.controller.ts:2142-2147`; jwoStatus-only `job-work-order.controller.ts:1274-1281, 1336-1342, 1403`; deliberately-opposite pair `dyeing.controller.ts:2278-2288` + `printing.controller.ts:2258-2268`. Legacy-only gates: `grn.service.ts:2612`, `dyeing.controller.ts:1902/2223`, `manufacturing-alerts.service.ts:96/229`, `stockMovement.service.ts:1622-1637`. Fix: make `jwoStatus` the single authority (one write helper maps the legacy alias until the column is dropped), add the CANCELLED exclusion to every legacy-status gate (copy `job-work-statutory.service.ts:140`), give "returned unprocessed" its own enum value. Effort: **M**. Found by 3 of 5 sweeps.

### 2. The sale-order status wears three hats — and the live B2B buyer app reads it
One status field tries to say three things at once: is the order confirmed, how much stock is reserved, and how much has shipped. The stock-reservation code overwrites it without checking what it says now, so releasing reserved stock on a partly-shipped order flips the House of Kasya buyer's badge back to "not shipped" — and after that the order can mathematically never reach "Delivered" (the delivery confirmation only writes onto dispatch statuses), so the B2B app polls forever; reserving stock against a cancelled order also quietly resurrects it. This touches daily warehouse allocation and every buyer-facing order badge.
**Technical:** `sale_orders.status`. Unguarded writers `saleOrder.service.ts:553-556` (deallocate), `:626-629` (allocate — no status precondition at all); guarded writers `dispatch.controller.ts:1003-1037, 1449-1476`. Declared state machine is dead code and stale (`stateMachine.ts:72-80` — never invoked for saleOrder, lacks DELIVERED). Extra traps: `updateSaleOrderSchema` accepts a `status` field the service silently drops (`saleOrder.schema.ts:93`), and the DRAFT check sits outside the item-rewrite transaction (`saleOrder.service.ts:169-199`). Fix: store only the commercial state and derive allocation/dispatch progress at read time, or one shared recompute helper that ranks dispatch facts above allocation and uses the guarded-updateMany style everywhere; add DELIVERED to the declared machine; drop `status` from the update schema. Effort: **M**. Found by 2 of 5 sweeps. External contract: `docs/B2B_INTEGRATION_GUIDE.md:94-95`.

### 3. "CAD approved" exists at two levels that drift — and the style-level stamp bypasses the price gate
A style can be stamped CAD-approved while none of its actual CAD rows are approved — the live database has about 30 such styles right now, including STYSW-002 (only row still pending) and LNG104 (rows geometry-approved but never price-approved). The cost-sheet screen accepts the style-level stamp as a full pass, skipping the "geometry approved AND price approved" gate installed on 2026-08-22 — recreating exactly the ₹0-fabric-rate cost sheets that fix was built to stop; meanwhile the production dashboard and the cutting gate give opposite answers about the same style. This touches costing/quotation daily.
**Technical:** `styles.cadStatus`/`approvedCadDate` vs `fabric_width_cad.approvalStatus`/`costingApprovalStatus`. One-sided writers: `style.service.ts:2302-2308` and `cad-approval.controller.ts:158-164` (style only), `cad-approval.controller.ts:227-234` (row only, never advances the style). Bypass: `style-costing-calc.controller.ts:122`; the code already patches known drift at read time in two places (`style.controller.ts:72`, `cad-planning.controller.ts:4392`) but the gate doesn't use them. Fix: derive the style-level state from the rows via one shared transactional helper called by all approve/reject/delete paths, delete the `:122` bypass, retire the legacy `POST /cad-planning/approve` route. Effort: **M**. Found by 4 of 5 sweeps.

### 4. The central stock ledger silently drifts below the detailed stock tables
Stock lives in two places — the per-lot tables and the central Stock Levels page — kept equal only by each piece of code remembering to post the change to both. Several live flows post one side only: returning unprocessed greige from a dyer/printer, and cancelling or deleting a cutting batch — each such event leaves the central ledger permanently lower (with no transaction trace), so the Stock Levels page under-reports and MRP over-orders material the factory already holds. The commit-time guard for this pattern exists and works, but these exact writers are grandfathered in its exception list.
**Technical:** `greige_stock`/`fabric_stock` vs `stock_levels`. Unsynced writers: `dyeing.controller.ts:2229-2236`, `printing.controller.ts:2210-2217` (greige return credit, no ledger row either), `cutting.controller.ts:486-513, 1113-1144` (batch delete/cancel restore) — all listed in `scripts/hooks/stock-sync-baseline.json`; latent: `WeightedAverageCostService.ts:156-242` (unrouted today). Fix: add the mirroring `syncStockLevelQuantity` calls plus transaction-ledger rows (a `returnGreigeStock()` in the service, mirroring `consumeGreigeStock`), remove these files from the baseline so the ratchet holds, and promote `backend/scripts/repair-quantity-drift.ts` from manual tool to scheduled reconciliation. Effort: **S–M**. Found by 3 of 5 sweeps (two distinct writer sets).

### 5. An invoice can be fully settled yet stay "overdue" forever once a credit note is involved
Amount-owed is tracked two ways — a running balance (payments plus credit notes) and a recomputation from payments alone — and the status label uses the payments-only math. An invoice settled by part credit note plus part payment gets stuck at PARTIALLY_PAID or OVERDUE permanently (no further payment can arrive to fix it, because the balance guard rejects overpaying), so accounts keeps dunning a customer who owes nothing; worse, merely editing that invoice later silently re-adds the credited amount to the receivable, desyncing the ERP from Tally. Undetonated so far (0 credit notes in the live DB) but the credit-note approval screen is live, so the first real credit note arms it.
**Technical:** `invoices.balanceAmount` vs status derived from `totalAmount−paidAmount`. Writers: `invoice.service.ts:179-205` + `:998-1000` (recordPayment status recompute ignores balance), `creditNote.service.ts:359-385` (decrements balance only — correctly), `invoice.service.ts:834-841` (updateInvoice recomputes balance from total−paid, erasing the credit). Fix: one shared `deriveStatus(total, balanceAmount, dueDate)` called by all three writers; updateInvoice must preserve approved-credit decrements (or extend the delete-path CN guard to money edits). Effort: **S**. Found by 2 of 5 sweeps.

### 6. Rejecting a CAD stamps the rejector's name into the "approved by" fields — and one gate still trusts them
One of the two rejection flows records the rejector's name and time in the approver columns; the other clears them properly and uses the dedicated rejected-by fields. A production gate then picks its comparison baseline by "has an approver name" instead of "is approved," so a freshly rejected CAD — carrying the newest timestamp — becomes the baseline, and the >3% fabric over-consumption approval gate is computed against rejected geometry: false blocks on good markers, or silent passes on bad ones. This is the same proxy shape the 2026-08-22 fix removed from order.controller; this second site was missed.
**Technical:** `fabric_width_cad.approvedBy/approvedAt`. Writers: `cad-approval.controller.ts:334-345` (rejector stamped into approver fields; its own response relabels it at `:364`) vs `style.service.ts:2348-2362` (correct `rejectedBy/rejectedAt`). Surviving proxy consumer: `cad-planning.controller.ts:3646-3655` (`approvedBy:{not:null}` ordered by `approvedAt desc`). Fix: rejection writes rejected* and clears approved*; the baseline query filters `approvalStatus:'APPROVED'`; add a smart-check ratchet banning `approvedBy:{not:null}` filters on this table. Effort: **S**. Found by 4 of 5 sweeps.

### 7. Purchase-order status echoes with no checks, a mislabeled "approver," and a dormant parallel engine
The dyeing/printing modules copy job status onto the paired purchase order unconditionally — they can flip a cancelled PO back to SENT or RECEIVED — while the job-work module's own cancel forgets the echo entirely, leaving a live-looking PO for a dead job that a GRN can still be booked against (double procurement: MRP re-orders while the PO claims received). Separately, "Approved by" on POs actually records whoever clicked Send, and a second, unrouted PO transition engine with contradictory rules (overwrites remarks, un-receives requirements) sits one route registration away from re-activating.
**Technical:** `purchase_orders.status` + `approvedById`. Unconditional writers: `dyeing.controller.ts:1847-1853, 2161-2175, 2293-2299`, `printing.controller.ts:1821, 2154, 2273`; missing cascade: `job-work-order.controller.ts:1208-1282`; sender stamp: `purchaseOrder.service.ts:825-830`; dormant divergent suite: `po-status-manager.service.ts:239-351` (its cancelPO reverts RECEIVED requirements — the MRP-24 class); admin override never engages (`purchaseOrder.controller.ts:353` omits userRole). Fix: funnel every status write through the validateTransition state machine; one shared shadow-PO echo helper called from all six process sites and JWO cancel (or derive the shadow PO's status from `jwoStatus` at read time); delete the dormant suite; display "Sent by" instead of "Approved by." Effort: **M**. Found by 2 of 5 sweeps.

### 8. The CAD "purpose" tag is stored twice, synced by hand, and the cutting gate reads only one copy
The workflow tag (costing / raw-material / production) lives in a legacy text column and a newer typed column, kept equal only by a two-line ritual copied at 10+ places — and several creation paths skip it, most notably the "Create Version" button, which produces rows the cutting-release gate cannot see while the cutting chart still displays them. The team would see "PRODUCTION CAD missing" blocking cutting on a style whose CAD is on the screen. Live data is currently clean (0 of 114 rows divergent, after a past backfill), but one routine UI click re-arms it.
**Technical:** `fabric_width_cad.purpose` vs `purposeEnum`. One-sided/neither writers: `cad-approval.controller.ts:410` (createPlanningVersion copies string only), `cad-planning.controller.ts:219-232, 1234-1247`, `style-import.service.ts:786-799`. Split readers: enum-only gate `productionBlockingValidation.service.ts:466-476` vs string-only `style-costing-calc.controller.ts:103/114/142` vs coalescing `cutting.controller.ts:1661/1773`. Fix: make `purposeEnum` the single authored column (backfill legacy + fix the creators), give every gate one shared coalescing helper until the string is dropped, add a smart-check flagging writes touching one column without the other. Effort: **S** immediate patch, **M** full single-source. Found by 3 of 5 sweeps.

### 9. The "preferred width" checkbox is owned by CAD on paper but overwritten by price approvals
The same flag means "the CAD team's recommended width" to one module and "the currently price-approved option" to another — the costing controller even lists it among fields costing must never touch, then writes it in its own approve/unapprove cascades. Approving a price on width B silently erases the CAD team's explicit choice of width A (and an unapprove leaves no preference at all), reordering the cutting-chart document and flipping the recommended option with no trace. This is the leftover of the 2026-08-22 split: approvals got their own columns, this flag did not.
**Technical:** `fabric_width_cad.isPreferred`. Declared CAD-owned at `fabric-costing.controller.ts:923` yet written by `fabric-costing.controller.ts:1437-1473, 1531-1538, 1877` and rejection cascades `cad-approval.controller.ts:344`, `style.service.ts:2360`; CAD writers `cad-planning.controller.ts:1612, 1722-1732`. Fix: the costing-primary option is fully derivable from `costingApprovalStatus==='APPROVED'` (partial unique index guarantees exactly one) — delete every costing-side isPreferred write and leave the flag purely CAD-owned. Effort: **S**. Found by 2 of 5 sweeps.

### 10. A cancelled work order can be resurrected by logging a cutting quantity
One flow decides "production hasn't started" by checking that a start-date field is empty instead of checking the status — and a work order cancelled before starting also has an empty start date. A stray production-tracking entry (stale screen, wrong pick, API client) flips the cancelled work order back to IN_PRODUCTION, stamps a start date, and nothing re-cancels it: a cancelled order shows live production and dashboards count it as active.
**Technical:** `work_orders.status`. Proxy guard `workOrder.service.ts:686-694` (`!actualStartDate`) vs the status-guarded sibling flows (`cutting.controller.ts:286-295`); cancel cascade `order.service.ts:547-555`; the completion recompute in the same file already refuses CANCELLED (`workOrder.service.ts:749-753`), proving intent. Fix: explicit `status==='PENDING'` precondition (or validateTransition) plus reject any tracking insert against a CANCELLED work order. Effort: **S**. Found by 1 sweep.

### 11. The "locked" flag is misread as "this is a real production costing"
The flag actually records "created via the costing promote flow," but screens read it as "genuine, immutable production costing" — so production CADs created from stock lots never count: the repeat-order shortcut doesn't fire, the style status card contradicts its own tabs, and those rows escape the "production CADs cannot be edited after locking" rule. Low severity — wrong badges, a missed convenience, and uneven edit discipline, no stock or money corruption — but reachable through a normal daily flow.
**Technical:** `fabric_width_cad.isLocked`. Sole true-writer `fabric-costing.controller.ts:1878`; unlocked PRODUCTION creator `cad-embroidery.controller.ts:568-610`; misreading consumers `fabric-costing.controller.ts:988-996, 1927`, `cad-planning.utils.ts:232-238`. Fix: either stamp `isLocked` in the stock-creation path, or read `purpose==='PRODUCTION'` (plus a price for "costed") in those consumers and demote isLocked to pure provenance. Effort: **S**. Found by 1 sweep.

## Overall health verdict

This bug class — one stored fact, two writers with different meanings — is the codebase's dominant structural failure mode: the 2026-08-22 fix cured one specimen, but eleven confirmed live siblings remain, concentrated exactly where two modules were bolted together (CAD↔costing, job-work↔PO, allocation↔dispatch, lot-stock↔central ledger), and three of them (JWO dual status, the cadStatus bypass, stock-ledger drift) have already diverged in live data. The encouraging half is that the guardrail culture demonstrably works: four scary-looking candidates verified safe precisely because a single disciplined writer or a real ratchet exists, so the winning pattern (one write path, derive don't duplicate, dedicated fields for dedicated meanings) is already proven in-house — it just hasn't been applied to these eleven. Every confirmed fix is small-to-medium effort, and adding the three proposed smart-check rules (ban approvedBy-not-null proxies, flag one-sided purpose writes, flag single-column JWO gates) would stop the class from regrowing after the cleanup.
